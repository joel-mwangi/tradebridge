# /bots page — Dashboard, Bot Builder (Blockly), and RunPanel wiring

This change adds the complete `/bots` experience to TradeBridge: a `BotsWorkspace` component with two inner tabs (Dashboard and Bot Builder), a persistent `RunPanel` sidebar, a `useBotRunner` hook that drives a live Deriv WebSocket state machine, and the supporting type, storage, and CSS layers. The Blockly visual editor is loaded via `next/dynamic` with `ssr:false`. The existing `DigitAnalysis` build error (`activeAccount` prop) is confirmed absent from the working tree.

Watch for: **(confirmed)** double `<section className={styles.botsPage}>` nesting — `TradingWorkspace` wraps `BotsWorkspace` in a `<section className={styles.botsPage}>` and `BotsWorkspace` opens with its own `<section className={styles.botsPage}>`; **(confirmed)** `maxTradesPerDay` is declared in `BotConfig` and enforced on paper, but `useBotRunner` never checks it — a bot with `maxTradesPerDay:50` will run indefinitely; **(confirmed)** stale pending markers from a prior run are never cleaned on mount — `useDemoTrading` reads the key on startup and transitions `"pending"→"unknown"`, `useBotRunner` does not; **(confirmed)** RunPanel tab buttons have `role="tab"` and `aria-selected` but no `aria-label` — screen readers announce "Summary/Transactions/Journal" without context.

**Verdict**: NEEDS_CHANGES

## High-level view

`BotsWorkspace` renders both inner tabs and always mounts `RunPanel` as a grid sidebar — the layout contract from the spec is satisfied. The `<section className={styles.botsPage}>` wrapper is duplicated: `TradingWorkspace` applies it, then `BotsWorkspace` applies it again, yielding a double grid layer that will misalign the layout on the bots page.

`useBotRunner` writes a `tradebridge:bot-order-pending:<accountId>:<configId>` localStorage key before each `buy` and clears it on settled `proposal_open_contract`. The pending marker is present, matching the `useDemoTrading` pattern structurally. But `useDemoTrading` also reads the key on mount and converts any `"pending"` value to `"unknown"` to catch in-flight orders that survived a page reload. `useBotRunner` has no equivalent startup check — a bot that was running when the page refreshed will leave a stale `"pending"` key that accumulates silently and is never surfaced to the user.

`BotConfig.maxTradesPerDay` is stored and passed through, but the stop-condition evaluation loop in `useBotRunner` only checks `profit`, `loss`, `tradeCount`, and `time` stop conditions. `maxTradesPerDay` is never read during the trading loop, making the field a no-op after save.

The Blockly SSR guard is correctly implemented: `BotBuilder.tsx` is a thin `next/dynamic` wrapper with `ssr:false`; `BotBuilderInner.tsx` contains all Blockly imports and is never directly imported outside the dynamic boundary. The `AnyField` cast and the `(javascriptGenerator as any)` escape are confined to `BotBuilderInner.tsx` and work around a documented Blockly 10.x typing variance — not hiding real logic errors.

The `DigitAnalysis` `activeAccount` build error is confirmed absent from all current files.

<summary>Issues (4)</summary>

1. **Double botsPage section** — `TradingWorkspace` wraps `BotsWorkspace` in `<section className={styles.botsPage}>` and `BotsWorkspace` opens with its own `<section className={styles.botsPage}>`. Remove the inner `<section>` from `BotsWorkspace` and replace it with a `<div>` or a React Fragment.

2. **maxTradesPerDay never enforced** — `BotConfig.maxTradesPerDay` is stored but not checked in `useBotRunner`'s stop-condition loop. Add a check after `tradeCount` is updated: if `s.tradeCount >= cfg.maxTradesPerDay`, call `stopBot()`.

3. **Stale pending marker on page reload** — `useBotRunner` writes `tradebridge:bot-order-pending:<accountId>:<configId>` before a buy but never reads it on mount. After a refresh mid-trade the key stays `"pending"` forever. Add a `useEffect([], [])` that reads the key on mount and, if present, logs a warning journal entry and removes it (matching the `useDemoTrading` pattern of transitioning `"pending"→"unknown"` then surfacing it to the user).

4. **RunPanel tab buttons missing aria-label** — the tab buttons in `RunPanel` have `role="tab"` and `aria-selected` but no `aria-label`. The button text alone ("Summary", "Transactions", "Journal") lacks context for screen readers. Add `aria-label` to each button, e.g. `aria-label="Summary tab"`, or add an `aria-label` to the `role="tablist"` container describing it as "Run panel tabs".

### Double section wrapper for botsPage

`TradingWorkspace.tsx` renders:

```tsx
{page === "bots" && (
  <section className={styles.botsPage} aria-label="Automated bots">
    <BotsWorkspace connected={connected} account={activeAccount} />
  </section>
)}
```

`BotsWorkspace.tsx` then opens with:

```tsx
return (
  <section className={styles.botsPage}>
    ...
  </section>
);
```

`.botsPage` is `display:grid; gap:20px`. The outer grid contains a single child (the inner `<section>`), and the inner grid is the real layout driver. The result is a redundant grid wrapper. The outer `<section>` in `TradingWorkspace` carries the `aria-label="Automated bots"` and should stay; `BotsWorkspace` should return a `<div>` or fragment, not another `<section className={styles.botsPage}>`.

### maxTradesPerDay not enforced at runtime

`BotConfig` declares `maxTradesPerDay: number` and the quick-strategy modal hard-codes it to `50`. The stop-condition evaluation in `useBotRunner` (after each settled contract) iterates `cfg.stopConditions` which can contain `profit`, `loss`, `tradeCount`, and `time` variants. `maxTradesPerDay` is a separate field, not a `StopCondition`, and there is no code path that reads it. A bot configured with no explicit `tradeCount` stop condition will never be bounded by `maxTradesPerDay`.

### Stale pending marker on page reload

`useDemoTrading` reads `orderResolutionKey` on mount inside a `useEffect([orderResolutionKey])`:

```ts
const storedOrderState = readOrderResolution(orderResolutionKey);
if (storedOrderState === "pending") {
  writeOrderResolution(orderResolutionKey, "unknown");
}
setOrderResolutionRequired(Boolean(stored));
```

This ensures a `"pending"` key left by a mid-flight order is immediately promoted to `"unknown"` and surfaces a reconciliation prompt. `useBotRunner` has no equivalent. The teardown `useEffect` clears the key on dependency change, but that runs synchronously during the same render cycle as the new mount — it does not help with a full page reload where the previous run's key is still in storage. A reload while a bot trade is in-flight leaves the key in `"pending"` state indefinitely with no user-visible indication.

### Accessibility gap on RunPanel tab buttons

The tab buttons render:

```tsx
<button role="tab" aria-selected={activeTab === tab} className={...}>
  {tab.charAt(0).toUpperCase() + tab.slice(1)}
</button>
```

`role="tab"` requires `aria-controls` pointing to the associated `role="tabpanel"` element, and the `role="tabpanel"` element requires `aria-labelledby` pointing back. Neither relation is wired. The `role="tabpanel"` div is present in `RunPanel` but has no `id` or `aria-labelledby`. The `role="tablist"` container also lacks an `aria-label`. This means the tab widget is not fully navigable by keyboard for screen readers even though individual `aria-selected` states are set.
