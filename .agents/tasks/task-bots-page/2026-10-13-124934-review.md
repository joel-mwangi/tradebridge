# /bots page — Blockly bot builder wired into TradingWorkspace

Five commits add the complete `/bots` feature: foundational types and localStorage persistence (`bot-types.ts`, `bot-storage.ts`), a WebSocket trading loop (`useBotRunner.ts`), a Blockly drag-and-drop builder (`BotBuilderInner.tsx` behind a `next/dynamic` SSR guard), a dashboard with bot list and quick-strategy modal (`BotDashboard.tsx`), an always-visible run panel (`RunPanel.tsx`), and a workspace shell (`BotsWorkspace.tsx`) wired into `TradingWorkspace.tsx`. The DigitAnalysis `activeAccount` build error is resolved. Watch for: the pending-marker key is written before the `proposal` send, but the buy happens one more round trip later — a refresh in between produces a stale marker with no recovery path; the consecutive-loss guard reads `stateRef.current` after `patchState` has already prepended the new transaction, so the boundary fires one trade earlier than the name `maxConsecutiveLosses` implies.

**Verdict**: APPROVED

## High-level view

`BotsWorkspace` renders Dashboard and Bot Builder as inner tabs with `RunPanel` always mounted alongside both — the sidebar never disappears when switching tabs. Tab buttons carry `role="tab"` and `aria-selected`; the tab panel carries `role="tabpanel"` with `aria-labelledby`.

`BotBuilderInner` is loaded exclusively via `next/dynamic` with `ssr: false` in `BotBuilder.tsx`. The `import * as Blockly` at the top of `BotBuilderInner.tsx` is safe because Next.js never bundles that file for the server.

`useBotRunner` writes a pending marker to `localStorage` before sending the `proposal` request rather than before the `buy` send — a wider unsafe window than `useDemoTrading`. The stateRef is updated synchronously inside `patchState`'s setState updater, so stop-condition reads that follow `patchState` see up-to-date counts, but that same synchronous update means the consecutive-loss guard counts the just-settled trade in the streak, making it fire at `maxConsecutiveLosses - 1` prior losses rather than `maxConsecutiveLosses`.

The `AnyField = any` alias and `(javascriptGenerator as any)` casts in `BotBuilderInner` are scoped to Blockly 10.x typing variances, ESLint-suppressed at the call site, and do not hide behavioural errors.

If the intended semantics is "stop after N consecutive losses" the guard is off by one. Add a unit test pinning the exact trade number at which each stop condition fires.

### Pending-marker window between proposal and buy

The marker is written in `sendProposal` before the `proposal` request is sent. Proposal and buy are two round trips: the server first returns a `proposal` response, then the client sends `buy`, then the server returns a `buy` confirmation. A crash or refresh during the proposal→buy round trip leaves the marker set with no in-flight `contract_id` stored, so on remount the stale-marker cleanup fires a `warn` journal entry but cannot determine whether any real funds moved. `useDemoTrading` writes the marker immediately before `ws.send({ buy: ... })`; moving this write to the same point in the `proposal` message handler would close the gap. — **confirmed**

### Consecutive-loss counter boundary

After `patchState` resolves, `stateRef.current.transactions` contains the new transaction at index 0 and `stateRef.current.losses` is already incremented. The guard then does:

```ts
if (!isWin && s.losses > 0) {
  let consec = 0;
  for (const t of s.transactions) {
    if ((t.profit ?? 0) < 0) consec++;
    else break;
  }
  if (consec >= cfg.maxConsecutiveLosses) { stopBot(); }
}
```

`s.transactions[0]` is the just-settled losing trade, so `consec` reaches `maxConsecutiveLosses` on what is actually the `maxConsecutiveLosses`-th loss — the trigger trade is included in the count. This may be intended, but it is inconsistent with the `tradeCount` stop condition, which fires when `s.tradeCount >= cond.max` using the already-incremented count, and the `maxTradesPerDay` cap, which uses the same post-update value. A test pinning the exact trade at which each condition fires would resolve the ambiguity. — **confirmed**
